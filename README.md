# Параметризуемый FIR-фильтр

FIR-фильтр на Verilog с программируемыми коэффициентами, настраиваемыми
разрядностями и конвейером. Проект включает проверку RTL через Python и
Icarus Verilog, а также конфигурацию OpenROAD Flow Scripts для оценки
таймингов, площади и мощности на Nangate45.

[Запуск симуляции](#проверка-rtl) · [Запуск OpenROAD](#синтез-и-оценка-ppa-в-openroad) · [Результаты прогона на 500 МГц](#результаты-прогона-на-500-мгц)

## Проверка RTL

Нужны Python 3 и Icarus Verilog (`iverilog` и `vvp`). На Ubuntu их можно
установить командой `sudo apt-get install python3 iverilog`. Выполняйте
команды из корня проекта.

```bash
python3 sim/test_fir.py &&
    iverilog -g2012 -I sim/build -s tb_test -o sim/build/tb_test.vvp \
        rtl/fir_filter.v sim/tb_test.sv &&
    vvp sim/build/tb_test.vvp
```

Python записывает входы, коэффициенты и эталонные результаты. Тестбенч
сравнивает выход с эталоном и при успехе выводит `[TB] RESULT : PASS`.
Параметры тестов и запись временной диаграммы описаны в [документации симуляции](sim/README.md).

## Параметры и интерфейс

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `X_WIDTH` | 14 | Разрядность signed-входа и signed-выхода |
| `H_WIDTH` | 14 | Разрядность signed-кода коэффициента |
| `TAPS` | 15 | Число коэффициентов |
| `PIPE_MUL` | 1 | Регистр после умножителей |
| `PIPE_SUM` | 1 | Регистр после всей суммы произведений |
| `PIPE_ROUND` | 1 | Регистр после округления |

Разрядности и `TAPS` должны быть положительными, `PIPE_*` — равны 0 или 1.
RTL не содержит автоматических проверок допустимости параметров.

| Сигнал | Назначение |
| --- | --- |
| `clk` | Работа по положительному фронту |
| `rst` | Синхронный сброс, активный высокий уровень, приоритет над `ce` |
| `ce` | Приём нового входа и продвижение всего конвейера |
| `x` | Signed-код входного отсчёта |
| `h` | Упакованные signed-коды коэффициентов |
| `y` | Зарегистрированный signed-результат |
| `y_valid` | Признак достоверности текущего `y` |

При `ce=0` все регистры, история, `y` и `y_valid` удерживаются. Это пауза,
а не вставка нулевого отсчёта. Каждый фронт с `rst=0, ce=1` принимает новый
вход; отдельного входного `valid` и механизма `ready` нет.

## Коэффициенты и математическая модель

Коэффициент при `x[n-k]` задаётся signed-кодом `H_k` в срезе
`h[k*H_WIDTH +: H_WIDTH]`.

`H_0` расположен в младших разрядах. При стандартных настройках
`h[13:0]` относится к текущему входу, `h[27:14]` — к предыдущему,
`h[209:196]` — к входу с задержкой 14 принятых отсчётов.

Число дробных разрядов коэффициента `D = H_WIDTH - 1`, реальный коэффициент
равен `H_k / 2**D`. Его диапазон: от −1 до `1 - 2**(-D)`.
Для `H_WIDTH=1` доступны только коэффициенты −1 и 0, дробной части нет.

Коэффициенты не хранятся отдельно. `x` и весь набор `h` должны быть стабильны
с соблюдением setup/hold около разрешённого фронта. На этом фронте текущие
коэффициенты применяются к новому входу и истории до её сдвига. Уже захваченные
промежуточные результаты сохраняют эффект прежних коэффициентов.

Индекс `n` увеличивается только при приёме входа. Начальная история нулевая.
Для каждого отсчёта используется набор коэффициентов, действующий на фронте
его приёма. Сумма и выход вычисляются так.

```text
S[n] = sum(x[n-k] * H_k[n], k = 0 ... TAPS - 1)
Y[n] = sat(roundEven(S[n] / 2**D))
```

Произведение имеет `X_WIDTH + H_WIDTH` бит, аккумулятор —
`X_WIDTH + H_WIDTH + ceil(log2(TAPS))` бит. При стандартных настройках
это 28 и 32 бита соответственно. Вход и выход имеют одинаковый масштаб.

Округление выполняется к ближайшему целому, половины — к чётному.
`1.5 → 2`, `2.5 → 2`, `−1.5 → −2`, `−2.5 → −2`.
В Python это правило записано через целочисленное деление с остатком.

```python
scale = 1 << D
q, r = divmod(total, scale)
rounded = q + int(2 * r > scale or (2 * r == scale and q % 2 != 0))
```

После округления применяется насыщение до диапазона
`[-2**(X_WIDTH-1), 2**(X_WIDTH-1)-1]`. Для 14 бит это −8192…8191.
Вся эталонная арифметика выполняется целыми числами, без `float`.

## Конвейер

```text
x и история → умножители → [PIPE_MUL] → сумма → [PIPE_SUM]
            → округление → [PIPE_ROUND] → насыщение → регистр y
```

В RTL объявлены вычисляемые константы:

```text
PIPE_STAGES = (PIPE_MUL == 1) + (PIPE_SUM == 1) + (PIPE_ROUND == 1) + 1
LATENCY = PIPE_STAGES - 1
```

Если вход принят на разрешённом фронте `E0`, результат появляется после
`E_LATENCY`. При `PIPE_*=1` это `E3`: четыре ступени и три интервала между
захватом входа и обновлением выхода. При `PIPE_*=0` выход обновляется уже на `E0`.
Паузы `ce=0` увеличивают задержку в физическом времени.

После сброса `y_valid=0`; первый достоверный результат появляется после
`PIPE_STAGES` разрешённых фронтов, считая первый приём. Нулевая начальная
история допустима, ждать заполнения всех `TAPS` отводов не требуется.
Затем `y_valid` остаётся единицей до сброса, в том числе на паузах.
Удерживаемый выход на паузе не является новым результатом.

## Синтез и оценка PPA в OpenROAD

Прогон использует стандартные параметры RTL (`X_WIDTH=H_WIDTH=14`,
`TAPS=15`, все `PIPE_*=1`). В синтезе `h` остаётся 210-битным входом
с программируемыми коэффициентами. Платформа `nangate45` использует типовую
библиотеку Nangate на основе модельного техпроцесса FreePDK45.
[Конфигурация Nangate45 в ORFS](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts/blob/master/flow/platforms/nangate45/config.mk), [описание FreePDK45](https://eda.ncsu.edu/freepdk/freepdk45/)

### 1. Подготовить окружение

После скачивания или распаковки проекта откройте Bash в каталоге с этим
`README.md` и папкой `rtl/`. Выберите локальную установку или Docker.
Команды настройки и прогона выполняйте в одной сессии Bash.

#### Вариант A. Без Docker на Ubuntu

Для установки с нуля используйте Ubuntu 24.04, в том числе под WSL 2
на Windows. Понадобятся интернет и права `sudo` для установки зависимостей.
OpenROAD Flow Scripts (ORFS) устанавливаем рядом с проектом. Первый запуск
`build_openroad.sh` соберёт OpenROAD и Yosys из исходников.
[Локальная установка ORFS](https://openroad-flow-scripts.readthedocs.io/en/latest/user/BuildLocally.html), [настройка WSL](https://openroad-flow-scripts.readthedocs.io/en/latest/user/BuildWithWSL.html)

```bash
FIR_ROOT=$(pwd -P)
ORFS_ROOT="$(dirname "$FIR_ROOT")/OpenROAD-flow-scripts"

sudo apt-get update
sudo apt-get install -y git
git clone --recursive https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts.git "$ORFS_ROOT"
(
    cd "$ORFS_ROOT" && sudo ./setup.sh && ./build_openroad.sh --local
)
```

Если ORFS уже установлен, задайте `ORFS_ROOT` абсолютным путём к существующей
копии и начните с этого блока. По хешу коммита можно восстановить версию
сценариев ORFS для повторного прогона.

```bash
FIR_ROOT=$(pwd -P)
ORFS_ROOT=${ORFS_ROOT:-"$(dirname "$FIR_ROOT")/OpenROAD-flow-scripts"}
ORFS_DESIGN_CONFIG="$FIR_ROOT/syn/config.mk"

git -C "$ORFS_ROOT" rev-parse HEAD

orfs() (
    cd "$ORFS_ROOT/flow" && source ../env.sh && WORK_HOME="$FIR_ROOT/syn/work" "$@"
)
```

#### Вариант B. С Docker

Запустите уже установленный Docker или воспользуйтесь инструкцией установки
для своей ОС. Готовый образ содержит инструменты и платформу. Идентификатор
образа (`digest`) нужен, чтобы повторить прогон на той же версии.
[Установка Docker](https://docs.docker.com/get-started/get-docker/), [Docker в ORFS](https://openroad-flow-scripts.readthedocs.io/en/latest/user/DockerShell.html)

```bash
FIR_ROOT=$(pwd -P)
ORFS_DESIGN_CONFIG=/work/syn/config.mk

docker pull openroad/orfs:latest
ORFS_IMAGE=$(docker image inspect --format '{{index .RepoDigests 0}}' openroad/orfs:latest)
printf '%s\n' "$ORFS_IMAGE"

orfs() {
    docker run --rm --user "$(id -u):$(id -g)" \
        --volume "$FIR_ROOT:/work" \
        --env WORK_HOME=/work/syn/work \
        --workdir /OpenROAD-flow-scripts/flow \
        --entrypoint bash "$ORFS_IMAGE" \
        -c 'source ../env.sh && exec "$@"' bash "$@"
}
```

#### Проверка окружения

```bash
mkdir -p syn/work
orfs yosys -V
orfs openroad -version
orfs make DESIGN_CONFIG=designs/nangate45/gcd/config.mk synth
```

Встроенный пример `gcd` проверяет доступ к библиотеке и запись результатов
в `syn/work/results/nangate45/gcd/base/`. В новой сессии Bash повторите
настройку функции `orfs` и её переменных. Чтобы воспроизвести запуск через
Docker с сохранённой версией инструментов, задайте `ORFS_IMAGE` digest образа.

### 2. Конфигурация и запуск FIR

`CORE_UTILIZATION=35` задаёт целевую долю площади ядра, занятую ячейками,
при расчёте размеров блока. `PLACE_DENSITY_LB_ADDON` добавляет запас к нижней
границе плотности глобального размещения. Эти настройки заданы в готовом
[syn/config.mk](syn/config.mk). [Переменные конфигурации ORFS](https://openroad-flow-scripts.readthedocs.io/en/latest/user/FlowVariables.html)

Временные ограничения заданы в готовом [syn/constraint.sdc](syn/constraint.sdc).
В Nangate45 время задаётся в наносекундах, ёмкость — в фемтофарадах.

| Ограничение | Значение | Что моделирует |
| --- | --- | --- |
| Период `fir_clk` | 2 нс | Целевую частоту 500 МГц |
| Входные задержки `min` / `max` | 0,05 / 0,30 нс | Раннее и позднее прибытие `x`, `h`, `ce` и `rst` относительно тактового фронта |
| Выходные задержки `min` / `max` | −0,05 / 0,30 нс | 0,05 нс удержания после фронта и 0,30 нс запаса до фронта захвата у внешнего приёмника |
| Входной фронт и нагрузка | 0,20 нс / 20 фФ | Время перехода на входах и ёмкость на каждом выходе |

Задержки и нагрузка портов описывают условный интерфейс. При интеграции их
уточняют по параметрам источника, приёмника и соединений.

```bash
orfs make "DESIGN_CONFIG=$ORFS_DESIGN_CONFIG" synth &&
    orfs make "DESIGN_CONFIG=$ORFS_DESIGN_CONFIG" finish
```

`synth` разворачивает параметры RTL в Yosys и отображает логику на ячейки
Nangate45. `finish` рассчитывает размеры блока, размещает ячейки, строит
дерево тактирования (CTS), трассирует соединения и формирует итоговый отчёт.
Финальный статический анализ таймингов (STA) учитывает сопротивления и
ёмкости соединений из `6_final.spef`.
[Этапы и отчёты ORFS](https://openroad-flow-scripts.readthedocs.io/en/latest/tutorials/FlowTutorial.html)

### 3. Отчёты и артефакты

ORFS сохраняет файлы под `syn/work/` в деревьях `reports/`, `logs/` и
`results/`. Для FIR путь внутри каждого дерева — `nangate45/fir_filter/base/`.

```bash
reports=syn/work/reports/nangate45/fir_filter/base
logs=syn/work/logs/nangate45/fir_filter/base

less "$reports/6_finish.rpt"
grep -E ' cells$|Chip area' "$reports/synth_stat.txt"
grep 'Design area' "$logs/6_report.log"
```

| Файл | Что в нём смотреть |
| --- | --- |
| `reports/…/synth_check.txt` | Проверка связности синтезированного нетлиста в Yosys |
| `reports/…/synth_stat.txt` | Количество ячеек, разбивка по типам и `Chip area` после синтеза |
| `reports/…/6_finish.rpt` | Критические пути, `report_clock_min_period`, проверки фронтов и нагрузки, таблица `report_power` |
| `logs/…/6_report.json` | Численные метрики setup, hold, Fmax, площади и мощности |
| `logs/…/6_report.log` | Журнал финального этапа, строка `Design area` и заполнение ядра |
| `reports/…/5_route_drc.rpt` | Нарушения, обнаруженные детальным трассировщиком |
| `reports/…/final_placement.webp`, `final_routing.webp`, `final_worst_path.webp` | Визуализация размещения, трассировки и критического пути |
| `results/…/1_2_yosys.v` | Синтезированный Verilog-нетлист |
| `results/…/6_final.gds`, `6_final.def`, `6_final.v`, `6_final.spef` | Финальная топология, геометрия размещения, нетлист и паразитные параметры соединений |

В `6_finish.rpt` секция `report_checks -path_delay max` показывает худший
setup-путь, а `-path_delay min` — худший hold-путь. `Startpoint` и `Endpoint`
указывают начало и конец пути. Отрицательный `slack` означает нарушение.
`WNS` показывает худшее отрицательное отклонение, `TNS` — сумму отрицательных
запасов по конечным точкам. `max_slew`, `max_capacitance` и `max_fanout`
проверяют длительность фронта, ёмкость и нагрузку по числу подключённых входов.
[Скрипт отчёта ORFS](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts/blob/master/flow/scripts/report_metrics.tcl)

В `report_power` значения приведены в ваттах. `Internal` показывает
динамическую мощность внутри ячеек, `Switching` — мощность на переключение
цепей, `Leakage` — утечки. Для оценки с реальным сценарием работы используют
VCD или SAIF с подходящей частотой и проверяют покрытие активности через
`report_activity_annotation`. Функциональный тестбенч задаёт период 8 нс
и постоянные коэффициенты в течение прогона. Для оценки мощности при
500 МГц нужен сценарий с периодом 2 нс. [Анализ мощности в OpenSTA](https://github.com/The-OpenROAD-Project/OpenSTA/blob/master/doc/Examples.md#power-analysis)

### Результаты прогона на 500 МГц

Прогон ORFS в Docker дошёл до `finish`. FIR с 15 отводами и всеми
включёнными ступенями конвейера выполнил требования setup и hold на 500 МГц
при заданных ограничениях и типовом угле Nangate45. Финальный STA учитывает
паразитные параметры трассировки из `6_final.spef`.

| Показатель | Значение |
| --- | --- |
| Целевой период и условия | 2 нс (500 МГц), `nangate45`, типовой угол, 1,1 В, 25 °C |
| Число ячеек и их площадь после синтеза | 13 467 ячеек, 28 434,34 мкм² |
| Стандартные ячейки после трассировки, без заполнителей | 13 634 ячейки, 28 329,5 мкм², 35,0% площади ядра |
| Размеры и площадь блока по DEF | 287,03 × 287,03 мкм, 82 386,22 мкм² |
| Худший setup slack и setup TNS | +0,35947 нс и 0 нс, 0 нарушений |
| Худший hold slack и hold TNS | +0,012394 нс и 0 нс, 0 нарушений |
| Критический setup-путь | `h[84]` → `result[6].with_pipeline.product_reg[27]` |
| Минимальный период и Fmax по STA для полученной схемы | около 1,64 нс и 609,56 МГц |
| Мощность при статистической активности | 7,767 мВт суммарно, в том числе 4,702 мВт internal, 2,587 мВт switching и 0,478 мВт leakage |
| Электрические проверки | 0 нарушений slew, capacitance и fanout |
| Детальная трассировка и логическая эквивалентность (LEC) | 0 нарушений правил трассировки, синтезированный и финальный нетлисты эквивалентны |

Худший setup-путь проходит от младшего бита коэффициента отвода с индексом 6
через умножитель до старшего бита регистра произведения. На hold самый
маленький запас, около 12 пс, получился на пути от `h[0]` до младшего бита
регистра произведения нулевого отвода. Fmax около 610 МГц — расчётная оценка
STA для топологии, полученной при ограничении 500 МГц.

При сборке `6_final.gds` KLayout сообщил о разнице единиц базы данных
DEF и GDS. Сборка завершилась, топология записана.

Исходные отчёты этого прогона сохранены в `syn/reports/`.

- Число ячеек и площадь после синтеза — [synth_stat.txt](syn/reports/synth_stat.txt).
- Критические пути, оценка частоты и таблица мощности — [6_finish.rpt](syn/reports/6_finish.rpt).
- Точные значения slack, площади ячеек и мощности — [6_report.json](syn/reports/6_report.json).

В журналах указаны `Yosys 0.68+post` и `OpenROAD unknown`.
Для точного воспроизведения окружения требуется digest использованного
образа Docker.
